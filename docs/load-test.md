## 시나리오 1: 30초 하트비트 + 팝오버 폴링 (`polling.js`)

1차 구조(FRND-3)예요. 사용자마다 30초에 한 번 `PUT /api/v1/presence`, 팝오버를 연 사용자는 30초에 한 번 `GET /api/v1/friends`. 모두 팝오버를 열어 둔 최악의 경우(`POPOVER=1`)로 재요.

`constant-arrival-rate`(open 모델)를 써요. 서버가 느려져도 앱은 30초마다 보내니까, 응답을 기다린 뒤 다음 요청을 보내는 기본 방식(closed 모델)으로는 서버가 실제보다 튼튼해 보여요.

| 사용자 | 초당 요청 | p95 하트비트 / 친구 | max | dropped | 앱 CPU | DB 커넥션 대기 | 워밍업 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1,000 | 67 | 9.5 / 8.1ms | 189ms | 0 | 약 0.2 | 0 | 안 함 (재시작 직후) |
| 2,000 | 133 | 8.3 / 5.8ms | 664ms | 0 | 약 0.19 | 0 | 안 함 |
| 4,000 | 267 | 3.8 / 2.7ms | 76ms | 0 | 약 0.32 | 0 | 1,000명 1분 |
| 6,000 | 400 (실제 395) | 1.17s / 1.64s | 2.91s | 835 | 0.32~1.0 | 최대 255 | 4,000명 직후 |
| 6,000 (Redis 풀 적용) | 400 (실제 368) | 3.05s / 4.68s | 9.8s | 5,812 | 0.30~1.0 | 최대 379 | 1,000명 1분 |

- 앱 CPU는 1코어 기준 비율(`process_cpu_usage`), 시작 30초를 뺀 평균이에요.
- **6,000명은 실패했어요.** 요청의 20.6%(14,637건)가 500이에요. 원인은 아래 [6,000명에서 무너진 이유](#6000명에서-무너진-이유)에 있어요.
- **Redis 풀을 켜고 다시 재도 실패했어요.** 요청의 19.6%(13,002건)가 500이에요. 포트 고갈은 사라졌고 원인이 달라요. 아래 [Redis 연결 풀을 켠 뒤 다시 잰 결과](#redis-연결-풀을-켠-뒤-다시-잰-결과)에 있어요.
- 워밍업 없이 잰 1,000명·2,000명은 JIT 최적화가 덜 된 상태라 4,000명과 바로 비교하면 안 돼요.

### 요청당 비용

워밍업한 4,000명 기준: CPU 0.32코어 ÷ 초당 267건 ≈ **요청 하나에 CPU 약 1.2ms**.

사용자 1명은 초당 약 0.067건(하트비트 + 폴링)을 보내요. 앱 CPU를 70%까지만 쓴다고 하면 맥의 1코어로 약 0.7 ÷ 0.0012 ≈ 580건/초, 약 8,700명이에요. VPS vCPU는 맥 코어보다 느려서 실제로는 이보다 적어요. 실제 사양에서 다시 재야 해요.

다만 CPU에 닿기 전에 6,000명에서 Redis 연결 문제로 먼저 무너졌어요 (아래).

### 발견한 것

- **워밍업 차이가 커요.** 워밍업 없이 잰 2,000명은 최대 0.6초짜리 응답이 테스트 중간에 띄엄띄엄 나왔어요. 워밍업 후 잰 4,000명은 요청이 2배인데도 최대 76ms였어요. 이 무렵 GC 원인에 `CodeCache GC Threshold`(JIT가 만든 코드 공간이 참)가 보여서, JIT 최적화가 몇 분에 걸쳐 이어진 영향으로 봐요.
- **DB 커넥션은 여유가 많아요.** 4,000명에서도 대기 0, 사용 중인 커넥션도 대부분 0이에요. 커넥션을 쥐는 시간이 평균 약 0.1ms라 금방 돌려줘요 (`hikaricp_connections_usage_seconds` 합 ÷ 횟수). 하트비트·친구 목록이 초당 약 270번 빌려도 리틀의 법칙으로 계산하면 평균 동시 0.03개쯤이에요.
- **1코어에서는 Serial GC예요.** GC 동안 앱 전체가 멈춰요. 4,000명에서 멈춤은 최대 약 9ms였어요.

### 6,000명에서 무너진 이유

CPU가 아니라 **Redis 연결을 요청마다 새로 열고 닫는 코드** 때문이에요.

**증상**: 실패 14,637건이 모두 같은 예외예요.

```text
RedisConnectionFailureException: Unable to connect to Redis
  Caused by: java.net.BindException: Cannot assign requested address
  at PresenceStore.findAll(PresenceStore.java:100)
```

`Cannot assign requested address`는 연결을 열 때 쓸 **내 쪽 포트가 남아 있지 않다**는 뜻이에요.

**원인**:

1. `PresenceStore.findAll()`은 여러 사람 상태를 한 번에 읽으려고 `executePipelined`를 써요. Lettuce는 평소에 연결 하나를 모든 요청이 같이 쓰지만, 파이프라인은 **전용 연결**이 필요해요. 연결 풀이 없어서 부를 때마다 TCP 연결을 새로 열고 닫아요.
2. 먼저 닫은 쪽(앱)에는 연결이 **TIME_WAIT 상태로 60초** 남아요. 그동안 그 포트는 다시 못 써요.
3. 컨테이너가 보낼 때 쓰는 포트는 32768~60999, **28,232개**예요. 그래서 초당 새 연결은 28,232 ÷ 60 ≈ **470개**가 한계예요.
4. 요청 하나가 여는 연결 수:
   - 하트비트: `find()`를 두 번 불러서(바꾸기 전·후 비교) **2개**
   - 친구 목록: `findAll()` 한 번이라 **1개**

| 사용자 | 초당 하트비트 × 2 + 친구 목록 × 1 | 60초 동안 쌓이는 TIME_WAIT | 포트 28,232개 |
| --- | --- | --- | --- |
| 4,000 | 133 × 2 + 133 = 400개/초 | 약 24,000 | 남음 |
| 6,000 | 200 × 2 + 200 = 600개/초 | 약 36,000 | **모자람** |

**확인**: 4,000명으로 80초 돌리면서 앱 컨테이너의 Redis 쪽 TIME_WAIT를 셌어요. 15초마다 약 6,000개씩(초당 400개) 늘다가 60초쯤 약 25,000개에서 멈췄어요. 계산과 같아요.

**같이 일어난 일**: 에러가 약 1분 간격으로 몰려왔어요(TIME_WAIT가 풀리는 주기). 그 구간에는 예외와 스택 트레이스 로그(약 290만 줄)를 만드느라 CPU가 1.0까지 찼어요. 에러가 없는 구간의 CPU는 0.32~0.37로 4,000명과 비슷했어요.

DB 커넥션도 에러 구간에만 10개가 모두 차서 대기가 생겼어요 (14:32 UTC 255, 14:33 UTC 32). 그 밖의 시간에는 사용 중인 커넥션이 0~1개였어요. 커넥션을 빌린 횟수는 초당 330~530번으로 평소와 비슷했고, 쥐는 시간 평균도 가장 높을 때 1.8ms였어요(리틀의 법칙으로 계산하면 평균 동시 0.7개). 대신 가장 오래 쥔 시간이 276ms까지 길어졌어요. CPU 차례나 GC를 기다리는 동안 응답을 받은 스레드가 커넥션을 돌려주지 못했고, 막혔던 요청이 한꺼번에 몰리면서 순간적으로 10개가 모자랐어요. 로그에 DB 예외는 없었어요. 그래서 DB 커넥션 대기는 원인이 아니라 결과이고, 풀 크기를 늘릴 일이 아니에요.

**의미**: 실제 VPS도 같은 리눅스 포트 범위를 쓰니까, **서버 사양을 올려도 이 한계는 그대로예요.** 모두 팝오버를 연 경우 약 4,700명(470 × 30초 ÷ 사용자당 3개), 팝오버 30%면 약 6,100명에서 같은 일이 생겨요.

**고칠 방향** (따로 작업):

- Lettuce 연결 풀(`commons-pool2` + `spring.data.redis.lettuce.pool`)을 켜서 파이프라인 연결을 다시 쓰기 → 적용 (아래)
- 한 사람만 읽는 `find()`는 파이프라인 없이 공유 연결로 바로 읽기 (`HGETALL` 한 번)
- 하트비트에서 `find()`를 두 번 부르는 것 줄이기

### Redis 연결 풀을 켠 뒤 다시 잰 결과

원본: `loadtest/results/polling-6000-pool.txt` (2026-11-10 18:00~18:03 KST)

**바꾼 것**: `build.gradle`에 `org.apache.commons:commons-pool2`를 넣고, `application.yml`에 풀을 설정했어요.

| 설정 | 값 | 이유 |
| --- | --- | --- |
| `max-active` | 8 (기본값) | 리틀의 법칙으로 보면 평균 동시 사용은 1개도 안 될 것으로 봤어요. 몰릴 때를 생각해 기본값을 두고, 재 보고 모자라면 늘려요 |
| `max-idle` | 8 | `max-active`와 같게 둬요. 작으면 몰림이 끝난 뒤 남는 연결을 닫아서 TIME_WAIT가 다시 생겨요 |
| `max-wait` | 150ms | 기본값은 -1(무한 대기)이에요. 하트비트 p95 목표가 200ms라 그 안에서 기다리고, 넘으면 빨리 실패시켜요 |
| `min-idle` | 안 씀 | `time-between-eviction-runs`를 같이 정하지 않으면 효과가 없어요. 첫 요청이 연결을 열면 `max-idle` 덕분에 계속 남아요 |

**포트 고갈은 사라졌어요.**

| | 풀 적용 전 | 풀 적용 후 |
| --- | --- | --- |
| 앱의 Redis 쪽 소켓 | TIME_WAIT 계속 증가 (4,000명에서 약 25,000) | ESTABLISHED 8개, TIME_WAIT 0개 |
| `BindException` | 14,637건 | 0건 |
| 실패 원인 | `BindException: Cannot assign requested address` | `PoolException` ← `Timeout waiting for idle object` (150ms) |

**그런데 실패율은 비슷해요 (19.6%).** 실패 13,197건 모두 풀에서 150ms 안에 연결을 빌리지 못한 경우예요. 위치는 하트비트 8,278건(첫 번째 `find()` 6,490, 두 번째 1,788), 친구 목록 4,919건이에요.

시간 순서 (KST, Prometheus 15초 간격):

| 시각 | 초당 요청 | 500 / 초 | CPU | GC | 힙 | DB 대기 |
| --- | --- | --- | --- | --- | --- | --- |
| 18:00:45 시작 | 155 | 0 | 0.99 | | 140MB | 0 |
| 18:01:15~18:01:30 | 400 | 0 | 0.30 | minor만 | 110~130MB | 0 |
| 18:01:45 | 366 | 21 | 0.88 | 첫 major GC, 0.49초 멈춤 | 140MB | 39 |
| 18:02:00~18:02:30 | 260~300 | 150~280 | 1.0 | major GC 5초마다, 최대 0.86초 멈춤 | 230~360MB | 190~379 |
| 18:02:45~18:03:00 | 390~400 | 0~137 | 0.32 | 줄어듦 | | 0 |
| 18:03:15 | 394 | 21 | 0.68 | | | 47 |

- 18:01:15~18:01:30에는 6,000명(초당 400건)을 에러 0, CPU 0.30으로 처리했어요. 부하 자체는 버틸 수 있는 양이에요.
- 에러는 **첫 major GC가 일어난 18:01:45부터** 시작했어요.

**가설** (시점이 겹쳐서 가능성이 높지만 아직 확인하지 않았어요):

1. Serial GC의 major GC 동안 앱 전체가 0.5~0.86초 멈춰요.
2. 그동안 들어온 요청(초당 400건 × 0.86초 ≈ 340건)이 멈춤이 풀리자 한꺼번에 Redis 풀 8개를 달라고 해요.
3. 대부분 150ms 안에 못 빌려서 예외가 나요.
4. 예외마다 긴 스택 트레이스 로그를 남겨 쓰레기가 늘고(힙 140MB → 360MB), major GC가 5초마다 반복돼요.
5. 다시 1로 돌아가 1분 넘게 악순환이 이어져요.

포트 고갈 때와 구조가 같고 방아쇠만 달라요. "작은 멈춤 하나가 전체 장애로 커지는 구조"가 남아 있어요.

**시작 직후 실패**: 앱을 다시 켜고 1,000명 워밍업을 시작한 직후 5초 동안 같은 풀 대기 초과가 195건 났고, 그 뒤로는 0건이었어요. 풀이 연결 0개로 시작하고 JIT가 덜 데워진 영향으로 보여요(확인 필요). 배포할 때마다 같은 일이 생길 수 있어요.

**시작할 때 CPU 0.99**: 6,000명 시작 직후에는 요청이 초당 155건뿐인데 CPU가 0.99였어요. 4,001~6,000번 사용자는 처음 하트비트라 상태가 "바뀜"으로 잡혀 친구 알림(DB 조회 + 전송)이 한꺼번에 돈 영향일 수 있어요(확인 필요).

**다음에 볼 약한 고리**:

- 하트비트가 풀을 써요. 한 사람만 읽는 `find()`도 파이프라인을 타서, 풀을 빌리는 요청의 대부분이 하트비트예요. 공유 연결로 읽으면 풀에서 빌리지 않아요.
- 실패가 비싸요. 예외 하나에 긴 스택 트레이스 로그를 남겨, 실패할수록 CPU와 메모리를 더 써요.
- 1코어라 Serial GC예요. major GC 동안 앱 전체가 멈춰요.

## 남은 일

로컬에서는 앱 지표만 모았어요. Nginx는 없었고, Prometheus·Grafana는 떠 있었지만 컨테이너 자원을 재지 않았어요. 이 둘과 아래 대부분은 실제 서버에서 이어서 재요.

- 실제 서버에서 같은 스크립트로 확인하고 사양 정하기 (k6는 서버 밖 맥에서 돌려 Nginx·TLS·인터넷 왕복까지 포함)
- 컨테이너별 CPU·메모리 기록 (`docker stats`), Nginx·Prometheus·Grafana 포함
- GC 멈춤에서 시작하는 풀 대기 초과 악순환 끊고 6,000명 다시 재기, 그다음 CPU 한계까지 올려 보기
- 앱 재시작 직후 풀 대기 초과(배포 직후 상황) 다시 만들어 보고 줄이기
- 1,000명·2,000명을 워밍업 후 다시 재기
- WebSocket 1,000 연결, 폴링과 비교해 [realtime.md](realtime.md)의 전후 비교 표 채우기
